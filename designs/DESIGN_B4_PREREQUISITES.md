# B4 Prerequisite Patch Support

## Objective

Apply prerequisite patches before reviewing a patchset generated by b4. This
allows a series based on other, not-yet-merged series to be reviewed against
the combined tree instead of failing to apply.

Issue #49 also describes Patchew's `Based-on` tag and b4's change-ID and
message-ID metadata. This first implementation is intentionally limited to
the ordered `prerequisite-patch-id` lines emitted by b4.

## B4 Metadata

B4 accepts dependencies by change ID, message ID, or stable patch ID. When it
formats a series for sending, it preserves the higher-level dependency marker
and expands the dependency into one `prerequisite-patch-id` line per patch.
The generated patch IDs use `git patch-id --stable`, and their order is the
order in which the prerequisite patches must be applied.

For example:

```text
base-commit: 0b5e142ced4bcf20532da051934bd694d1bbd470
change-id: 20260724-example-dependent-series-dd1580754609
prerequisite-change-id: 20260714-example-prerequisite-41e5d1ca0dc3:v2
prerequisite-patch-id: 8723aa599dcf5b836fb81cf1efb6c9096bf60b7a
prerequisite-patch-id: 12754335ccf210bcdeaa8a5d60b2280618d50993
```

The stable patch IDs identify the exact patch content. The change-ID and
message-ID markers remain useful to people, but the expanded patch IDs are
sufficient for Sashiko to resolve and apply the dependencies.

## Ingestion and Local Lookup

Add a nullable `git_patch_id` column to `patches` and index it. Whenever an
email patch is ingested, calculate its ID with `git patch-id --stable` and
persist it with the diff. Failure to calculate an ID must not block normal
patch ingestion.

Existing rows are left nullable rather than performing an unbounded startup
backfill over a potentially large archive. A missing local ID falls through
to the lore lookup, so existing databases remain functional after migration.

"Local" means Sashiko's own database on the review server. It never refers to
the sender's Git checkout or workstation.

## Dependency Resolution

Parse `prerequisite-patch-id` only when it starts at the beginning of a line
and contains exactly one 40-character hexadecimal value. This avoids treating
quoted mail or prose examples as active metadata. Preserve the first-seen
order and discard duplicate IDs.

The reviewer already loads the cover-letter body, or the single patch body
when there is no cover. Resolve each parsed ID in this order:

1. Look for a matching `patches.git_patch_id` in Sashiko's database.
2. If it is absent, POST a `patchid:<id>` search to lore's public-inbox mbox
   endpoint, using the same query b4 uses.
3. Parse the returned thread, calculate stable IDs for its patch messages,
   and select the exact requested patch.

A lore search returns the full matching thread. Cache all patch messages from
that response for the current resolution operation so multiple prerequisites
from one series normally require one request. Downloads have compressed and
decompressed size limits and an HTTP timeout. Lore requests share one
process-wide HTTP client so concurrent and successive reviews reuse pooled
connections. Connection failures, timeouts, rate limits, and server errors are
retried twice with bounded backoff before dependency resolution fails.

When multiple locally stored revisions have the same stable patch ID, use the
newest matching message; equal stable patch IDs represent equivalent content
for application. Lore results are preparation inputs and are not submitted to
the normal ingestion pipeline, so fetching a dependency does not schedule a
second, unrelated review.

If lore cannot be reached or does not return the exact stable patch ID,
baseline preparation fails with a specific log entry naming the missing
prerequisite. Sashiko must not silently review a different tree.

## Worktree Preparation

Resolve prerequisite content once before trying baseline candidates. For
every candidate:

1. Create the worktree at the candidate's resolved commit as today.
2. Apply resolved prerequisite patches in metadata order.
3. Record the resulting prerequisite tip as the effective review baseline.
4. Apply the patchset being reviewed in its normal series order.

If a prerequisite fails on one baseline candidate, clean up that worktree and
try the next candidate. Baseline logs identify each prerequisite patch ID and
message ID, making dependency failures distinguishable from failures in the
target series.

The database baseline continues to describe the selected upstream commit.
The transient prerequisite tip is passed to the review worker as its baseline
so series-range analysis excludes prerequisite commits while the worktree and
source context still include their changes.

Prerequisite patches are preparation context only. They are not added to the
target patchset's review payload, do not receive duplicate reviews, and do not
alter the target patch-to-commit mapping.

## Concurrency

Dependency resolution reads immutable patch content. It does not depend on a
prerequisite patchset reaching `Reviewed`; a complete prerequisite series can
remain `Pending` or `In Review` while a dependent worktree applies its stored
patches. Concurrent review tasks use separate worktrees and separate
per-resolution lore caches.

## Testing

- Parser tests cover ordering, duplicate suppression, CRLF input, malformed
  IDs, and quoted metadata.
- Git helper tests verify stable patch-ID calculation.
- Database tests verify ID persistence, lookup, and schema migration.
- Mbox client tests verify shared transport, request methods, bounded transient
  retries, and non-retryable status handling.
- Resolver tests verify local hits, lore fallback, response caching, missing
  IDs, and bounded mbox processing without relying on the public network.
- Reviewer tests create a repository where the target patch fails on the base
  commit, then verify it succeeds after the prerequisite is applied and uses
  the prerequisite tip as its effective review baseline. Timestamp tests
  verify invalid dates fail explicitly instead of producing an empty header.
- Existing baseline and review tests protect behavior for patchsets without
  prerequisite metadata.

## Out of Scope

- Patchew `Based-on` tags.
- Resolving bare `prerequisite-change-id` or `prerequisite-message-id` values
  when b4 did not emit expanded patch IDs.
- Persisting lore-only dependency fetches as ordinary patchsets.
- Automatically requeueing an entire patchset after lore request retries are
  exhausted.
- Detecting that a prerequisite patch has already landed in a selected tree.
