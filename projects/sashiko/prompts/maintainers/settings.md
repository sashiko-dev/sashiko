## Settings Schema, Upgrade Compatibility, and Documentation Sync

- Installed user and operator configuration files (`~/.config/sashiko.toml`
  generated by earlier `sashiko init` releases, deployed `Settings.toml` files,
  and email policy files) persist on disk across binary upgrades. Updating
  `Settings.toml`, `docs/examples/`, and `docs/configuration.md` in lockstep
  only updates templates for new setups and does not migrate existing
  installations.
- Because configuration structs use `#[serde(deny_unknown_fields)]` to catch
  typos, removing or renaming any configuration key, table, or enum variant that
  existed prior to `Baseline SHA` (check `git_log` / `git_show` on
  `src/settings.rs`, `src/email_policy.rs`, `Settings.toml`, or
  `docs/examples/`) without a serde compatibility path breaks existing
  installations at startup and must be reported as High severity, even if the
  commit message states that breaking old files or deleting the line is
  expected:
  - When renaming a setting field or enum variant, keep `#[serde(alias = "...")]`
    for the old name.
  - When retiring or deprecating an obsolete setting, retain a
    `#[doc(hidden)] #[serde(default)]` optional no-op field (emitting a
    non-fatal deprecation warning when populated) rather than deleting the field
    from a `deny_unknown_fields` struct.
  - When adding a new setting, provide a backward-compatible `#[serde(default)]`
    so existing files omitting it continue to load, and update `Settings.toml`,
    `docs/examples/`, and `docs/configuration.md` in lockstep for active keys.
- Precedence order must be preserved: CLI flags override environment variables
  (`SASHIKO_*`), which override the selected configuration file
  (`--settings` / `SASHIKO_CONFIG` / `./Settings.toml` / `~/.config/sashiko.toml`),
  which overrides compiled defaults.

## Secret Masking in Settings

- Any new credential, token, password, or webhook secret field added to a
  settings struct must be masked (`"***"`) in custom `fmt::Debug`
  implementations and redacted via `redact_secret` whenever URLs or connection
  strings are logged.
- Never log or serialize raw `Settings` structs containing unredacted secrets into
  API responses or error messages.
