# MARVELL OCTEONTX2 RVU ADMIN FUNCTION DRIVER

This component implements key subsystems of the Marvell OcteonTX2/CN10K RVU Admin Function (AF) driver: NPC field-hash extraction and exact-match MAC table management (`rvu_npc_hash.c`/`.h`), switchdev/representor event notification and VLAN/MCAM rule steering (`rvu_rep.c`), internal LBK switch rule management (`rvu_switch.c`), SDP PF/VF identification and channel provisioning (`rvu_sdp.c`), register offset validation and definitions (`rvu_reg.c`/`.h`), hardware queue/context bitfields (`rvu_struct.h`), and mailbox/parser tracepoints (`rvu_trace.c`/`.h`).

## Architecture & Data Flow

- Adding (`rvu_npc_exact_add_table_entry`) or deleting (`rvu_npc_exact_del_table_entry_by_id`) an exact-match entry with `cmd == true` must call `__rvu_npc_exact_cmd_rules_cnt_update` with `+1` or `-1` so `table->cnt_cmd_rules[drop_mcam_idx]` and `rvu_npc_enable_mcam_by_entry_index` stay symmetric; 0-to-1 and 1-to-0 transitions must only toggle `rvu_npc_enable_mcam_by_entry_index` when `!promisc_mode[drop_mcam_idx]`, while `rvu_npc_exact_promisc_enable`/`disable` toggle only `promisc_mode` and the MCAM drop rule without modifying `cnt_cmd_rules`. [F5, F37]
- `rvu_exact_prepare_mdata` packs `mac` at `[47:0]`, `chan` at `[59:48]`, and `ctype` at `[61:60]`, applies `mask`, and left-shifts by 2 (`ldata << 2`) to MSB-align the 62-bit search key for `rvu_npc_toeplitz_hash`, whereas `rvu_exact_prepare_table_entry` keeps those fields unshifted at `[61:0]` with `enable` at bit 63. [F57]
- `rvu_exact_config_table_mask` and `rvu_exact_config_result_ctrl` must update `table->mem_table.mask`, `table->mem_table.hash_mask`, and `table->mem_table.hash_offset` in lockstep with `NPC_AF_INTFX_EXACT_MASK` and `NPC_AF_INTFX_EXACT_RESULT_CTL` so `rvu_exact_calculate_hash` matches hardware. `rvu_npc_exact_init` must verify `table->mem_table.depth` is a power of 2 before calling `rvu_exact_config_result_ctrl`, which sets `hash_mask = depth - 1` for bitwise AND bounding. [F34, F56]
- `table->mem_table.bmap` is a 0-based flat bitmap of size `table->mem_table.depth * table->mem_table.ways` where way `ways` (`0..ways-1`) and hash index `index` (`0..depth-1`) map to bit offset `index + ways * depth` in `rvu_npc_exact_alloc_mem_table_entry` and `rvu_npc_exact_dealloc_table_entry`. [F53]
- In `rvu_npc_exact_add_to_list`, `entry->list` must be inserted into `table->lhead_mem_tbl_entry[ways]` and `table->lhead_cam_tbl_entry` in ascending order of `entry->index`, because `rvu_dbg_npc_exact_show_entries` iterates `i` from `0` to `table->mem_table.depth - 1` and only advances `mem_entry[j]` when `mem_entry[j]->index == i`. [F68]
- Valid entries in `table->drop_rule_map` (`0..NPC_MCAM_DROP_RULE_MAX - 1`) must be packed contiguously from index 0 with no `valid == false` gaps, because `rvu_npc_exact_save_drop_rule_chan_and_mask`, `rvu_npc_exact_drop_rule_to_pcifunc`, and `rvu_npc_exact_get_drop_rule_info` stop scanning at the first `!valid` slot. [F55]
- Exact-match DMAC filter drop rules and promiscuous/MAC table operations in `rvu_npc_hash.c` are scoped strictly to CGX-mapped PFs (`RVU_PFFUNC(rvu->pdev, i, 0)`), so callers of `rvu_npc_exact_mac_addr_*` and `rvu_npc_exact_promisc_*` must verify `is_cgx_config_permitted` (or `is_pf_cgxmapped` for `mac_addr_set`). [F115]
- `rvu_npc_exact_disable_feature` may only be invoked after `rvu_npc_exact_can_disable_feature` verifies that `rvu->hw->cap.npc_exact_match_enabled` is true and `table->lhead_gbl` is empty under `table->lock`. [F117]
- In `npc_update_field_hash`, `NPC_AF_INTFX_HASHX_CFG(intf, hash_idx)` must have both `BIT_ULL(11)` and `BIT_ULL(12)` set before matching `ltype & ltype_mask`; under `NPC_LT_LC_IP6`, `!hash_idx` maps to `NPC_SIP_IPV6` (`pkt->ip6src`) and non-zero `hash_idx` maps to `NPC_DIP_IPV6` (`pkt->ip6dst`), and while hashing into the 32-bit `field_hash` in `entry`, it must still copy the unhashed 128-bit address and mask from `pkt`/`mask` into `opkt`/`omask`. [F43, F67]
- In `rvu_switch.c` and `rvu_rep.c`, `rswitch->entry2pcifunc` is indexed by the 0-based offset `entry` (`0` to `rswitch->used_entries - 1`), while hardware MCAM rules in `rvu_switch_install_rules`, `rvu_rep_install_mcam_rules`, and `rvu_switch_update_rules` must be addressed at `rswitch->start_entry + entry`. [F45]
- In `rvu_switch_enable`, `alloc_req.count` and `rswitch->entry2pcifunc` allocation size (`cgx_mapped_pfs + cgx_mapped_vfs`, multiplied by 4 when `rvu->rep_mode` is set) must match the 1 `entry2pcifunc` slot per PF/VF written by `rvu_switch_install_rules` and 4 slots per PF/VF written by `rvu_rep_install_mcam_rules`. [F59]
- When constructing `pcifunc` values in `rvu_switch_install_rules`, `rvu_switch_disable`, `rvu_rep_install_mcam_rules`, and `rvu_mbox_handler_get_rep_cnt`, `func == 0` is reserved for the PF itself (`!(pcifunc & RVU_PFVF_FUNC_MASK)`) while VF loop indices `0 <= vf < numvfs` must be converted to 1-based function IDs (`vf + 1`). [F60]
- In `rvu_rep_up_notify`, when `event->event & RVU_EVENT_MAC_ADDR_CHANGE` is set, the target `pfvf->mac_addr` must be updated from `event->evt_data.mac` when sending the `rep_event_up_notify` mailbox message to the PF. [F47]
- In `rvu_rep.c`, every request type registered in `MBOX_UP_REP_MESSAGES` must place `struct mbox_msghdr hdr` at offset 0 so `otx2_mbox_alloc_msg_ ## _fn_name` can safely cast the `struct mbox_msghdr *` returned by `otx2_mbox_alloc_msg_rsp` to `struct _req_type *`. [F86]
- In `rvu_sdp.c`, `rvu_sdp_init` must populate both `sdp_pf_num[i]` and `rvu->pf[sdp_pf_num[i]].sdp_info` for each SDP PF, because `is_sdp_pfvf` checks `sdp_pf_num[]` and `rvu_mbox_handler_set_sdp_chan_info` unconditionally dereferences `pfvf->sdp_info`. [F48]
- In `rvu_struct.h`, `struct nix_cn10k_rq_ctx_s` and `struct nix_rq_ctx_s` (and `struct nix_cn10k_sq_ctx_s` and `struct nix_sq_ctx_s`) must maintain identical total sizes (128 bytes) and keep `ena` at bit 0 of word 0, because `rvu_mbox_handler_nix_cn10k_aq_enq` casts `nix_cn10k_aq_enq_req`/`rsp` to `nix_aq_enq_req`/`rsp`. [F50]
- `txsch_reg_map` is indexed directly by `regblk` (`0 <= regblk < NIX_TXSCH_LVL_CNT`) in `rvu_check_valid_reg`, which then verifies `map->regblk == regblk`, so `txsch_reg_map` entries must appear in exact `NIX_TXSCH_LVL_SMQ`..`NIX_TXSCH_LVL_TL1` enum order and `num_ranges` must not exceed `MAX_REG_RANGES` (8). [F52]

## Synchronization

- `rvu_npc_exact_del_table_entry_by_id` invokes `rvu_npc_enable_mcam_by_entry_index` (which acquires `rvu->hw->mcam.lock`) while holding `rvu->hw->table->lock`, establishing the lock hierarchy `table->lock` -> `mcam->lock`; code holding `mcam->lock` must never acquire `table->lock`. [F12]
- Callers holding `mutex_lock(&table->lock)` must release `table->lock` before calling `rvu_npc_exact_alloc_id`, `rvu_npc_exact_free_id`, `rvu_npc_exact_dealloc_table_entry`, `rvu_npc_exact_update_table_entry`, or `rvu_npc_exact_del_table_entry_by_id`, which each acquire `table->lock` internally. In `rvu_npc_exact_reset`, `table->lhead_gbl` must be traversed with `list_for_each_entry_safe`, reading `iter->seq_id` and unlocking `table->lock` before calling `rvu_npc_exact_del_table_entry_by_id` (which unlinks and frees `iter`). [F72, F108]
- Callers of `__rvu_npc_exact_find_entry_by_seq_id` must hold `mutex_lock(&table->lock)` across the lookup and any access to the returned `struct npc_exact_table_entry`, copying out needed fields before unlocking if the entry is not unlinked. [F107]
- `rvu_rep_up_notify` and `rvu_rep_notify_pfvf_state` must acquire `rvu->mbox_lock` before calling `otx2_mbox_alloc_msg_rep_event_up_notify` and release `rvu->mbox_lock` both when message allocation returns `NULL` and after `otx2_mbox_msg_send_up` (and `otx2_mbox_wait_for_rsp` in `rvu_rep_up_notify`) completes. [F8]
- Because AF-PF mailbox handlers run under `rvu->mbox_lock`, `rvu_mbox_handler_rep_event_notify` must never call `rvu_rep_up_notify` synchronously; instead it allocates `struct rep_evtq_ent` with `GFP_ATOMIC`, queues it on `rvu->rep_evtq_head` under `rvu->rep_evtq_lock`, and schedules `rvu->rep_evt_work` on `rvu->rep_evt_wq`, while `rvu_rep_wq_handler` must unlink `qentry` under `rvu->rep_evtq_lock`, drop the spinlock before calling `rvu_rep_up_notify`, and unconditionally call `kfree(qentry)`. [F7, F105]

## Object Lifetimes

- When iterating PCI devices with `pci_get_device` in `rvu_sdp_init`, the loop body must not drop the device reference on each iteration because `pci_get_device` decrements the reference count of its input `pdev`, and `pci_dev_put(pdev)` must be called on early error return and after the loop terminates. [F1]
- `rvu_switch_enable` must free allocated MCAM entries via `rvu_mbox_handler_npc_mcam_free_entry` (and uninstall flows via `rvu_mbox_handler_npc_delete_flow` plus `kfree(rswitch->entry2pcifunc)` if rule setup fails). When `rvu_switch_disable` tears down switch mode, in `!rvu->rep_mode` it must revert every CGX-mapped PF and VF's default RX unicast rule `chan_mask` to `0xFFF` via `rvu_switch_install_rx_rule`, disable its LBK link via `rvu_switch_enable_lbk_link`, and delete the MCAM flows, and in all modes reset `rswitch->used_entries = 0` when freeing `rswitch->entry2pcifunc`. [F6, F44]
- `rvu_switch_install_rules` and `rvu_rep_install_mcam_rules` must call `rvu_get_nix_blkaddr(rvu, pcifunc)` for each PF and VF before installing rules, and `rvu_switch_install_rx_rule`/`rvu_switch_install_tx_rule` must skip hardware installation when `NIXLF_INITIALIZED` is not set in `pfvf->flags`. [F99]

## API Contracts

- In `rvu_npc_hash.c`, `rvu_npc_exact_alloc_id` and `rvu_npc_exact_get_drop_rule_info` return `bool` (`true` on success, `false` on failure), whereas `rvu_npc_exact_alloc_mem_table_entry`, `rvu_npc_exact_alloc_cam_table_entry`, and `rvu_npc_exact_alloc_table_entry` return `0` on success and negative errno on failure. [F18]
- In `rvu_npc_exact_get_drop_rule_info`, the `val`, `mask`, and `pcifunc` out-parameters are optional and may be `NULL`, but `drop_mcam_idx` is unconditionally dereferenced on both success and failure paths and must be non-`NULL`. [F23]
- `rvu_npc_exact_free_id` must only be called with a `seq_id` that was either just allocated by `rvu_npc_exact_alloc_id` or verified to exist in `table->lhead_gbl` via `__rvu_npc_exact_find_entry_by_seq_id`, because `rvu_npc_exact_free_id` calls `clear_bit(seq_id, table->id_bmap)` without bounds-checking `seq_id` against `table->tot_ids`. [F88]
- `npc_config_secret_key` and `npc_update_field_hash` must check `rvu->hw->cap.npc_hash_extract` before accessing `NPC_AF_INTFX_SECRET_KEY*` or `NPC_AF_INTFX_HASHX_CFG` registers. `rvu_npc_exact_init` only allocates `rvu->hw->table` and sets `rvu->hw->cap.npc_exact_match_enabled` when both `NPC_AF_CONST3` bit 62 and `NPC_EXACT_NIBBLE_HIT` in `NPC_AF_INTFX_KEX_CFG(NIX_INTF_RX)` are set, so callers must gate `rvu_npc_exact_*` table operations on `rvu_npc_exact_has_match_table(rvu)`. [F92, F93]
- In `KEX_LD_CFG_USE_HASH`, `KEX_LD_CFG_HASH`, `NPC_AF_INTFX_LIDX_LTX_LDX_CFG`, and `NPC_AF_INTFX_EXACT_CFG`, the `bytesm1` field encodes the extracted byte length minus 1 (e.g., 3 for 4 bytes, `0xf` for 16 bytes, `ETH_ALEN - 1` for 6 bytes), and `hdr_ofs` in `KEX_LD_CFG_HASH` must be a 64-bit value (`ULL`) because it is shifted left by 32. Consequently, `npc_program_mkex_hash` must only enable IPv6 hash extraction (`mh->lid_lt_ld_hash_en[intf][NPC_LID_LC][NPC_LT_LC_IP6][ld] = true`) when `hdr_offset` is 8 or 24 and hardware `FIELD_GET(NPC_BYTESM, cfg) == 3` (4 extracted bytes). [F29, F116]
- Callers of `rvu_npc_wide_extract` must pass `width_bits` in `1..64` (avoiding `hi << lbits` UB and `u64` mask truncation issues). Callers of `rvu_npc_toeplitz_hash` must pass a mutable `key` array of at least `DIV_ROUND_UP(key_bit_len, 64)` `u64` words (which `rvu_npc_lshift_key` mutates in place, so it must not be reused) and `data` of at least `DIV_ROUND_UP(data_bit_len, 64)` `u64` words. Callers of `npc_field_hash_calc` must pass `u64 ldata[2]` with the upper 64 bits of the CPU-converted 128-bit field in `ldata[1]` and the lower 64 bits in `ldata[0]`. [F58, F78, F83]
- When AF-internal helpers (`rvu_rep_install_rx_rule`, `rvu_rep_install_tx_rule`, `rvu_switch_install_rx_rule`, `rvu_switch_install_tx_rule`) call `rvu_mbox_handler_npc_install_flow` to install an MCAM rule on behalf of a target `pcifunc`, they must set `req.hdr.pcifunc = 0` and pass the target function in `req.vf`. [F113]
- In `rvu_reg.c`, `rvu_check_valid_reg` requires 8-byte aligned register offsets (`!(reg & 0x07)`) and checks `txsch_reg_map` ranges using a half-open interval (`reg >= start && reg < end`), so `reg_range.end` must be set to one past the last valid 64-bit register offset (`last_offset + 8`). [F28]
- Callers of `trace_otx2_parse_dump` (in `rvu_trace.h`) must pass a `u64 *word` pointer backed by at least 6 contiguous `u64` words (48 bytes) because `TP_fast_assign` unconditionally dereferences `*(word + 0)` through `*(word + 5)`. [F85]

## Error Handling

- In `rvu_npc_exact_add_to_list`, any failure after `rvu_npc_exact_alloc_id` must release `*seq_id` via `rvu_npc_exact_free_id` (and `kfree(entry)` if allocated), and in `rvu_npc_exact_add_table_entry`, failure of `rvu_npc_exact_add_to_list` must release the table slot via `rvu_npc_exact_dealloc_table_entry`. [F4]

## Known Pitfalls

- In PF iteration loops across `rvu_switch.c` and `rvu_rep.c` (`rvu_switch_install_rules`, `rvu_switch_disable`, `rvu_rep_install_mcam_rules`, and `rvu_mbox_handler_get_rep_cnt`), `rvu_get_pf_numvfs(rvu, pf, &numvfs, ...)` must be called on every PF iteration before using `numvfs` as the VF loop bound. [F25]
- Stack-allocated mailbox request structures in `rvu_switch.c` and `rvu_rep.c` (`npc_install_flow_req`, `npc_mcam_alloc_entry_req`, `npc_delete_flow_req`, `npc_mcam_free_entry_req`, `nix_vtag_config`) must be zero-initialized before calling `rvu_mbox_handler_*()` directly. [F26]
- Because `npc_mkex_hash_default` is defined `static` in `rvu_npc_hash.h`, each translation unit has a distinct copy; all runtime readers and writers of MKEX hash state must access `rvu->kpu.mkex_hash` (initialized in `rvu_npc.c`) rather than referencing `npc_mkex_hash_default` directly. [F40]
- In `rvu_npc_hash.c`, `npc_update_use_hash` must read `NPC_HDR_OFFSET` and `NPC_KEY_OFFSET` from `NPC_AF_INTFX_LIDX_LTX_LDX_CFG(intf, lid, lt, ld)` before constructing the new `KEX_LD_CFG_USE_HASH` value, and `npc_program_mkex_hash_rx` and `npc_program_mkex_hash_tx` must be updated in lockstep. In both functions, `hash_cnt` must be checked against `NPC_MAX_HASH` before programming a hash entry and incremented only after the `SET_KEX_LD*` register writes so all `NPC_MAX_HASH` slots starting at 0 are programmed. [F41, F65]
- `rvu_npc_exact_alloc_table_entry` must initialize `*ways` to a value below `NPC_EXACT_TBL_MAX_WAYS` (`0`) even when allocating an `NPC_EXACT_OPC_CAM` entry, because `rvu_npc_exact_add_table_entry` passes an uninitialized stack variable `ways` and `rvu_npc_exact_add_to_list` evaluates `WARN_ON(ways >= NPC_EXACT_TBL_MAX_WAYS)` unconditionally. [F89]
- `rvu_npc_exact_update_table_entry` cannot in-place update an `NPC_EXACT_OPC_MEM` entry when `rvu_exact_calculate_hash` for `new_mac` differs from `entry->index`, so callers (`rvu_npc_exact_mac_addr_update` and `rvu_npc_exact_mac_addr_set`) must fall back to `rvu_npc_exact_del_table_entry_by_id` followed by `rvu_npc_exact_add_table_entry`. [F96]
- In `rvu_reg.h`, the `NPC_AF_MCAMEX_BANKX_*` and `NPC_AF_MATCH_STATX` macros implicitly evaluate `rvu->hw->npc_ext_set` from the caller's lexical scope to choose between legacy (`0x1000000`/`0x1800000`) and extended (`0x8000000`) register offsets. `NIX_AF_DWRR_MTUX(a)` (`0x790 | (a) << 16`) is only valid on CN10KB silicon where `hw->cap.nix_multiple_dwrr_mtu` is set; on other silicon, `0x790` is `NIX_AF_DWRR_SDP_MTU` and RPM/LBK use `NIX_AF_DWRR_RPM_MTU` (`0x7A0`). [F101, F102]
